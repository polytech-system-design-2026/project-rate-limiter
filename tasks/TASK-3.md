# Этап 3. Масштабирование

## Цель

Запустить сервис в двух экземплярах за балансировщиком так, чтобы лимиты оставались общими: счётчики переезжают в Redis, правила кэшируются и работают без PostgreSQL. Измерить эффект нагрузочным тестом.

## Что нужно сделать

1. **Сначала снимите базовые числа — до любых изменений.** На коде этапа 2 заполните `loadtest/locustfile.py` (сценарий — в разделе «Нагрузочный тест» ниже), поднимите сервис и запустите:

   ```bash
   make up
   make loadtest
   ```

   Сохраните итоговую таблицу locust: это колонка «один экземпляр» в отчёте.
2. Обновите `develop` после merge этапа 2 и поднимите этап:

   ```toml
   [tool.course]
   stage = "3_scaling"
   ```

3. Добавьте в `docker-compose.yml` сервис `redis` с `healthcheck`, порт наружу не публикуется.
4. **Счётчики в Redis.** Решение «пропустить или отклонить» должно быть общим для всех экземпляров. Проверка и увеличение счётчика — атомарно: два экземпляра не должны одновременно прочитать «9 из 10» и оба пропустить запрос. Подойдут `INCR` + `EXPIRE` для fixed window, sorted set в транзакции `MULTI`/`EXEC` или Lua-скрипт.
5. **Кэш правил в Redis.** `/resource` не ходит в PostgreSQL за правилами на каждый запрос. После `PUT /limits` новые правила видны обоим экземплярам сразу. Если PostgreSQL остановлен, `/resource` продолжает работать по действующим правилам.
6. **Два экземпляра за nginx:**
   - у `app` в compose — `deploy.replicas: 2`, порт `app` больше не публикуется;
   - сервис `nginx` публикует порт 8000 и проксирует запросы в `app:8000`. Docker отдаёт на имя `app` адреса обоих экземпляров, и nginx распределяет запросы между ними по очереди;
   - nginx должен передать адрес клиента: `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` — nginx сохранит пришедший заголовок и допишет в конец свой адрес, первый адрес останется клиентским.

   Пример `observability/nginx/nginx.conf` (или любой другой путь, смонтированный в `/etc/nginx/conf.d/default.conf`):

   ```nginx
   upstream app {
       server app:8000;
   }

   server {
       listen 8000;

       location / {
           proxy_pass http://app;
           proxy_set_header Host $host;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
       }
   }
   ```

7. **Заголовок `X-Instance`** в каждом ответе — hostname контейнера (`socket.gethostname()`): по нему видно, какой экземпляр ответил.
8. **Миграции — отдельным одноразовым сервисом.** Если оба экземпляра при старте выполняют `alembic upgrade head`, на пустой базе они одновременно создают одни и те же таблицы, и один из них падает. Сделайте сервис `migrate` из того же образа с командой `alembic upgrade head`, а `app` пусть стартует после него: `depends_on: migrate: condition: service_completed_successfully`.
9. `/health` проверяет и PostgreSQL, и Redis.
10. Не меньше 3 новых своих тестов.
11. Повторите нагрузочный тест с теми же параметрами и заполните раздел README «Нагрузочный тест».
12. Допишите в `docs/ARCHITECTURE.md` раздел `## Что изменилось на этапе 3`: где теперь счётчики и почему операция атомарна, как устроен кэш правил, как nginx распределяет запросы.

## Контракт

Эндпоинты те же, что на этапе 2. Добавляется:

- заголовок ответа `X-Instance` — имя экземпляра;
- порт 8000 на хосте публикует `nginx`, а не `app`.

Весь контракт этапа 2 продолжает действовать — теперь через nginx.

Что проверяет CI (`contract_tests/stage_3/`, плюс все тесты `stage_2/`):

- при `per_ip.limit = 10` через порт 8000 с одного адреса проходит ровно 10 запросов, 11-й — 429 (а не 20, как было бы с отдельными счётчиками у экземпляров);
- ответы приходят от двух разных экземпляров (`X-Instance`);
- `docker compose stop db` → `/resource` продолжает отвечать 200 и 429 по действующим правилам → `docker compose start db`. Тест сам возвращает БД в исходное состояние.

## Нагрузочный тест

Сценарий в `loadtest/locustfile.py`: 100 % запросов — `GET /resource` с 50 разных адресов в `X-Forwarded-For` (например, у каждого пользователя locust свой адрес). Ответ 429 здесь ожидаем — считайте его успехом (`catch_response=True` и `resp.success()`), ошибкой — только 5xx. Перед тестом выставьте через `PUT /limits` большой глобальный лимит, чтобы тест мерил сервис, а не упирался в общий лимит.

Параметры `make loadtest`: 50 пользователей, 10 новых в секунду, 1 минута. Параметры для одного и двух экземпляров должны совпадать.

## Критерии приёмки

- CI зелёный.
- Проверка и увеличение счётчика атомарны, и в `ARCHITECTURE.md` объяснено, за счёт чего.
- На горячем пути `/resource` нет запроса в PostgreSQL.
- Миграции не запускаются из двух экземпляров одновременно.
- Раздел README «Нагрузочный тест» с параметрами, таблицей и выводами.
- Не меньше 3 новых своих тестов.
- В `ARCHITECTURE.md` есть раздел «Что изменилось на этапе 3».

## Как проверить локально

```bash
make check
make up
make test-contract   # stage_2 и stage_3
make loadtest
```

Посмотреть, как nginx распределяет запросы:

```bash
for i in 1 2 3 4; do curl -s -o /dev/null -D - http://localhost:8000/resource | grep -i x-instance; done
```

Один экземпляр для замера «до»: `docker compose up -d --scale app=1`, затем `docker compose restart nginx`.

Посмотреть, что лежит в Redis: `docker compose exec redis redis-cli`, затем `KEYS *`.

## Типичные ошибки

- **Счётчики остались в памяти процесса** — через nginx с одного адреса проходит 20 запросов вместо 10. Тест это поймает.
- **Чтение и запись счётчика — две отдельные команды** (`GET`, потом `SET`): под нагрузкой два экземпляра пропускают лишние запросы. Нужна атомарная операция.
- **Оба экземпляра запускают миграции** — один из них падает при старте, и CI видит только один экземпляр.
- **nginx затирает `X-Forwarded-For`** (`proxy_set_header X-Forwarded-For $remote_addr`) — все клиенты становятся адресом хоста, per-IP лимит превращается в глобальный.
- **У `app` остался `ports: "8000:8000"`** — с двумя репликами порт не поделить, а nginx не сможет его занять.
- **nginx стартует раньше `app`** и падает, не найдя имя `app`: добавьте `depends_on`.
- **После `docker compose restart app` nginx несколько секунд отвечает 502** — это нормально: он временно исключает упавшие экземпляры. Тесты ждут `/health` перед продолжением.
- **Кэш правил не сбрасывается после `PUT /limits`** — один экземпляр применяет новые правила, другой старые.
- **Тест с остановленной БД падает на ожидании `/health`.** При остановленном PostgreSQL `/health` отвечает 503 — так и должно быть, тест ходит не в `/health`, а в `/resource`.
