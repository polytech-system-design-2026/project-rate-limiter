# Этап 1. Архитектура

## Цель

Спроектировать сервис до написания кода: оценить нагрузку, выбрать хранилища, описать модель данных, потоки данных и контракт API в формате OpenAPI. Заодно — настроить репозиторий и окружение и пройти весь путь сдачи через pull request.

## Что нужно сделать

### Репозиторий и окружение

1. Впишите ФИО, GitHub-ник и тему (`rate-limiter`) в таблицу группы — ссылка в стартовом сообщении курса. Дождитесь, когда на почту придёт приглашение в организацию `polytech-system-design-2026`, и примите его.
2. Откройте [шаблон](https://github.com/polytech-system-design-2026/project-rate-limiter), нажмите «Use this template» → «Create a new repository»:
   - Owner — `polytech-system-design-2026`;
   - Repository name — `project-rate-limiter-<ваш GitHub-ник>`;
   - видимость — Private.
3. Склонируйте репозиторий и перейдите в него:

   ```bash
   git clone https://github.com/polytech-system-design-2026/project-rate-limiter-<ник>.git
   cd project-rate-limiter-<ник>
   ```

4. Поставьте uv и Docker Desktop — команды для macOS, Linux и Windows в [README](../README.md#установка-окружения). Затем:

   ```bash
   make install
   make hooks
   ```

5. Создайте ветку `develop` — вся работа идёт в ней:

   ```bash
   git switch -c develop
   ```

6. Впишите в [README](../README.md) свои ФИО и группу вместо комментария в строке «Студент».

### Архитектура

7. Заполните [`docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md). Разделы «Сценарии», «Функциональные требования» и «Контракт API» уже заполнены — это требования заказчика. Ваша часть отмечена строками `> TODO:`:
   - **оценка нагрузки** в «Нефункциональных требованиях»: RPS в среднем и в пике отдельно на чтение и на запись, объём данных за год, размер кэша. Покажите арифметику: из каких чисел что получилось;
   - **модель данных**: таблица правил — типы полей, ключи, ограничения; где и в какой структуре живут счётчики;
   - **компоненты и потоки данных**: схема в блоке `mermaid` и пара абзацев о том, как проходят запрос к `/resource` и изменение правил. Подпишите стрелки: кто кого вызывает, что читает и что пишет;
   - **выбор хранилища и алгоритма**: какой алгоритм лимитирования (fixed window, sliding window, token bucket) и почему, почему правила в PostgreSQL, что на этапе 3 уедет в Redis.

   Строки `> TODO:` удалите, когда замените их своим текстом.
8. Напишите [`docs/openapi.yaml`](../docs/openapi.yaml) — спецификацию API в формате OpenAPI 3.x для всех операций из раздела «Контракт» ниже.

   Зачем писать руками, если FastAPI генерирует спецификацию сам? Сгенерированная спецификация описывает то, что уже написано. Здесь порядок обратный: сначала проектируем контракт — пути, тела, коды ошибок, — потом реализуем его. На этапе 2 CI сверит спроектированные операции с реализованными, и расхождение сделает его красным.
9. Проверьте локально (раздел «Как проверить локально») и сдайте (раздел «Как сдать»).

Кода сервиса на этом этапе нет. Этап принимается до того, как вы начнёте писать код: так вы получите замечания по архитектуре, пока их дёшево учесть.

## Контракт

Операции, которые должны быть в `docs/openapi.yaml`, с кодами ответов:

| Метод | Путь | Тело | Ответ | Коды |
|---|---|---|---|---|
| GET | `/resource` | — | `{"message": "ok"}` | 200; 429 — `{"detail": "rate limit exceeded", "retry_after": 7}` + заголовок `Retry-After: 7` |
| GET | `/limits` | — | `{"global": {"limit": 100, "window_seconds": 60}, "per_ip": {"limit": 10, "window_seconds": 60}}` | 200 |
| PUT | `/limits` | то же тело | то же | 200; 422 |
| GET | `/health` | — | `{"status": "ok"}` | 200 |

Опишите в спецификации заголовок ответа `Retry-After` у 429 и заголовок запроса `X-Forwarded-For` у `/resource`.

Что проверяет CI (`contract_tests/stage_1/`):

- в `docs/ARCHITECTURE.md` есть все семь разделов `##` из шаблона, в том же порядке;
- есть хотя бы одна схема в блоке ` ```mermaid `;
- не осталось ни одной строки, начинающейся с `> TODO:`;
- документ длиннее шаблона хотя бы на 1 500 символов (без пробелов);
- `docs/openapi.yaml` — валидный OpenAPI 3.x;
- в нём есть все операции из таблицы выше (имя параметра пути может быть любым) и все перечисленные коды ответов;
- у каждой операции есть `summary`.

## Критерии приёмки

- CI зелёный.
- В README вписаны ФИО и группа.
- Оценка нагрузки посчитана из чисел в требованиях, арифметика видна.
- Выбран и обоснован один алгоритм лимитирования; понятно, как он ведёт себя на границе окна.
- Понятно, где живут счётчики на этапе 2 и почему на этапе 3 они переезжают в Redis.
- Схема показывает потоки данных, а не только набор компонентов.
- Выбор хранилища объяснён через сценарии и оценку нагрузки.
- В `openapi.yaml` описаны ошибки, а не только успешные ответы.

## Как проверить локально

```bash
make check-stage-1   # проверки ARCHITECTURE.md и openapi.yaml
make check           # линтеры; тестов на этом этапе нет, это нормально
```

Чтобы посмотреть, как GitHub нарисует схему, откройте `docs/ARCHITECTURE.md` в своём репозитории на github.com после пуша. Спецификацию удобно смотреть в [Swagger Editor](https://editor.swagger.io/): вставьте содержимое `openapi.yaml` слева.

## Как сдать

1. Закоммитьте и запушьте `develop`:

   ```bash
   git add README.md docs/
   git commit -m "Add architecture and API design"
   git push -u origin develop
   ```

2. На GitHub откройте pull request из `develop` в `main` своего репозитория. Заполните шаблон описания, в Reviewers укажите `vladefr97`.
3. Дождитесь зелёного CI и напишите в чат курса: «project-rate-limiter, ник, этап 1, PR готов».
4. Замечания в PR исправляйте в `develop` и пушьте — PR обновится сам. Мержит преподаватель.

Подробно — в `Договоренности.md` курса.

## Типичные ошибки

- **Репозиторий создан в личном аккаунте.** В поле Owner при создании из шаблона нужно выбрать организацию. Если её там нет — приглашение ещё не принято. Исправить: удалить репозиторий и создать заново.
- **Видимость Public.** Репозиторий должен быть Private: Settings → General → Danger Zone → Change visibility.
- **PR из `main` в `main` или в шаблон.** Базовая ветка PR — `main` вашего репозитория, сравниваемая — `develop`. Если в списке репозиториев при создании PR виден `project-rate-limiter` без ника — вы открываете PR в шаблон.
- **CI красный, в логе: «остались незаполненные места с `> TODO:`».** В сообщении перечислены номера строк с `> TODO:` — замените эти строки своим текстом.
- **«В docs/openapi.yaml табуляция».** YAML не допускает табы. Включите в редакторе отступы пробелами (в VS Code — внизу справа «Spaces: 2») и замените табы.
- **Схема не рисуется на GitHub.** Блок должен начинаться строкой ` ```mermaid ` и закрываться ` ``` `, без пробелов перед обратными кавычками.
- **pre-commit исправил файлы и прервал коммит.** Это нормальная работа хуков: они форматируют код и убирают лишние пробелы. Добавьте исправленное (`git add -u`) и повторите `git commit`.
- **В коммите `.venv/`.** Его создаёт `make install`, в репозиторий он не нужен и уже есть в `.gitignore`. Если закоммитили: `git rm -r --cached .venv` и коммит.
- **`stage` в `pyproject.toml`.** На этом этапе оставьте `1_architecture`, как в шаблоне.
