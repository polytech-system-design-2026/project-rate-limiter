# Этап 2. MVP

## Цель

Реализовать спроектированный на этапе 1 контракт: сервис на FastAPI с данными в PostgreSQL, миграциями alembic и разделением на слои, который поднимается одной командой через docker compose.

## Что нужно сделать

1. Обновите `develop` после merge этапа 1 и поднимите этап в `pyproject.toml`:

   ```bash
   git switch main && git pull && git switch develop && git merge main
   ```

   ```toml
   [tool.course]
   stage = "2_mvp"
   ```

   С этого момента CI поднимает ваш сервис и гоняет контрактные тесты `contract_tests/stage_2/`.
2. Реализуйте сервис в `app/` со слоями:
   - `app/api/` — роутеры FastAPI и схемы запросов и ответов, без бизнес-логики;
   - `app/service/` — алгоритм лимитирования, определение IP клиента, работа с правилами;
   - `app/repository/` — запросы к PostgreSQL через SQLAlchemy 2.x (правила).
3. Настройте миграции alembic (`alembic init alembic`) и опишите таблицу первой миграцией. Приложение не создаёт таблицы само (`Base.metadata.create_all` не используется): миграции применяются при старте контейнера, например `alembic upgrade head && uvicorn ...`.
4. Напишите `Dockerfile` сервиса и `docker-compose.yml` в корне репозитория:
   - сервис `app` публикует порт 8000, uvicorn слушает `0.0.0.0:8000`;
   - сервис `db` — PostgreSQL с `healthcheck`, порт наружу не публикуется;
   - `app` стартует после готовности `db`: `depends_on` с `condition: service_healthy`.
5. Начальные правила — из переменных окружения `GLOBAL_LIMIT`, `PER_IP_LIMIT`, `WINDOW_SECONDS`: при старте, если правил в БД ещё нет, запишите их. Все остальные настройки тоже из переменных окружения. Реальные значения в `.env` (он в `.gitignore`), в репозитории — `.env.example` со всеми переменными, которые читает приложение. CI создаёт `.env` копированием `.env.example`, поэтому значения в нём должны подходить для запуска.
6. `GET /health` отвечает 200 `{"status": "ok"}`, только когда PostgreSQL доступен (выполните `SELECT 1`), иначе 503. По нему CI понимает, что сервис готов.
7. Напишите не меньше 5 своих тестов в `tests/`. Тесты проверяют логику — например, разбор `X-Forwarded-For` и алгоритм окна на подставном времени, — а не то, что вызвался мок.
8. Добавьте в README раздел «Запуск»: как поднять сервис и прогнать тесты.
9. Если по ходу реализации контракт в `docs/openapi.yaml` изменился — обновите спецификацию.

## Контракт

| Метод | Путь | Тело | Ответ | Коды |
|---|---|---|---|---|
| GET | `/resource` | — | `{"message": "ok"}` | 200; 429 — `{"detail": "rate limit exceeded", "retry_after": 7}` + заголовок `Retry-After: 7` |
| GET | `/limits` | — | `{"global": {"limit": 100, "window_seconds": 60}, "per_ip": {"limit": 10, "window_seconds": 60}}` | 200 |
| PUT | `/limits` | то же тело | то же | 200; 422 — `limit < 1`, `window_seconds < 1` |
| GET | `/health` | — | `{"status": "ok"}` | 200; 503 — БД недоступна |

- **Алгоритм** — один на выбор: fixed window, sliding window или token bucket; обоснование — в `ARCHITECTURE.md`. Тесты от алгоритма не зависят: при `limit = N` и окне `W` секунд серия из N быстрых запросов проходит, (N+1)-й получает 429, а через `W + 1` секунд запросы снова проходят. Тесты используют `W = 10`, чтобы у token bucket за время серии не успевало накопиться заметное число токенов.
- **Два правила одновременно**: запрос пропускается, только если не превышен ни глобальный лимит (все запросы к `/resource`), ни лимит его IP. Как считать отклонённые запросы — решите сами и опишите в `ARCHITECTURE.md`.
- **IP клиента** — первый адрес из заголовка `X-Forwarded-For` (`"203.0.113.7, 10.0.0.2"` → `203.0.113.7`); если заголовка нет — адрес соединения.
- **429**: тело `{"detail": "rate limit exceeded", "retry_after": <секунды>}` и заголовок `Retry-After` с тем же числом. `retry_after` — целое от 1 до размера окна. Обычный `HTTPException` сюда не подходит: он кладёт в тело только `detail`. Верните ответ целиком, например `JSONResponse(status_code=429, content={...}, headers={"Retry-After": str(retry_after)})`.
- **`PUT /limits`** заменяет оба правила, оба обязательны; ответ — сохранённые правила. Поле тела называется `global`, а это ключевое слово Python: в модели Pydantic назовите атрибут иначе и задайте `Field(alias="global")` вместе с `model_config = {"populate_by_name": True}`. Новые правила действуют сразу, без перезапуска, и переживают `docker compose restart app`.
- **Счётчики** на этом этапе могут жить в памяти процесса — это исправляется на этапе 3.
- Ошибки валидации — стандартные 422 FastAPI.
- Тела ответов тесты сравнивают целиком: лишних полей в них быть не должно.

Что проверяет CI (`contract_tests/stage_2/`). Тесты выставляют правила через `PUT /limits` в начале каждого теста, используют окно 10 секунд и уникальные адреса в `X-Forwarded-For`, поэтому от значений в `.env` не зависят:

- per-IP лимит: 5 запросов проходят подряд, 6-й — 429; отдельный тест проверяет, что после паузы длиннее окна запросы снова проходят;
- формат 429 и `Retry-After`;
- адрес A исчерпал лимит → A получает 429, адрес B — 200;
- запросы с `X-Forwarded-For: A` и `X-Forwarded-For: A, 10.1.2.3` — один клиент;
- глобальный лимит: `global.limit = 5`, per-IP большой; 3 запроса от A и 2 от B проходят, 6-й от C — 429;
- `PUT /limits` действует сразу; `GET /limits` возвращает сохранённое; 422 на неверные правила;
- после `docker compose restart app` правила на месте;
- операции (метод + путь) в `docs/openapi.yaml` совпадают с живым `GET /openapi.json`. `/health`, `/metrics`, `/docs`, `/openapi.json` в сравнении не участвуют.

Если выбран fixed window, граница окна может случайно попасть внутрь серии запросов теста. Поэтому сценарии с сериями повторяются до трёх раз; неверная реализация падает на каждой попытке.

## Критерии приёмки

- CI зелёный.
- Слои api / service / repository разделены, в роутерах нет бизнес-логики.
- Таблицы создаются миграциями alembic.
- Выбранный алгоритм обоснован в `ARCHITECTURE.md`.
- `.env.example` совпадает с тем, что читает приложение; `.env` и секретов в репозитории нет.
- Не меньше 5 своих тестов, и они проверяют логику.
- В README есть раздел «Запуск».

## Как проверить локально

```bash
make check           # линтеры, типы и ваши тесты
make up              # создаёт .env из .env.example (если его нет) и поднимает compose
make test-contract   # контрактные тесты этапа 2 против поднятого сервиса
make down            # остановить и удалить данные
```

Тест с перезапуском контейнера можно временно пропустить: `uv run python contract_tests/course.py test-contract -m "not restarts_containers"`. В CI он запускается всегда.

Посмотреть, что сервис пишет в лог: `docker compose logs app`. Документация API, которую генерирует FastAPI: http://localhost:8000/docs.

### Если CI красный

Откройте упавший прогон на вкладке Checks в PR:

- `lint` или `unit-tests` — то же, что `make check` локально;
- `meta` — неверное значение `stage` в `pyproject.toml`, сообщение скажет, какие допустимы;
- `stage-1-architecture` — сломали что-то в `docs/`;
- `contract` — разверните шаг, который упал:
  - «wait for /health» — сервис не поднялся. Причина — в шаге «docker compose logs» ниже: там вывод вашего приложения и БД;
  - «contract tests» — в выводе имя упавшего теста и сообщение, что ожидалось и что пришло. Тесты лежат в `contract_tests/stage_2/`, их можно прочитать.

## Типичные ошибки

- **uvicorn слушает `127.0.0.1`.** Внутри контейнера это адрес только самого контейнера, снаружи сервис недоступен. Нужно `--host 0.0.0.0`.
- **`/health` отвечает 200, пока БД ещё не готова.** Тогда тесты стартуют раньше времени и падают на первом же запросе. `/health` должен реально сходить в PostgreSQL.
- **Порт не 8000.** Тесты ходят на `http://localhost:8000`, в compose нужно `"8000:8000"`.
- **Таблицы создаются из кода** (`create_all`), а миграций нет или они не применяются при старте.
- **`.env` в репозитории.** Удалите из git (`git rm --cached .env`), проверьте, что он в `.gitignore`. Значения, которые туда попали, считайте скомпрометированными.
- **Поле `global` в модели Pydantic.** `global: Rule` — синтаксическая ошибка Python. Нужен другой атрибут плюс `Field(alias="global")`, иначе тело запроса не разберётся и тесты будут получать 422.
- **IP берётся из `request.client.host` даже при наличии `X-Forwarded-For`** — все тестовые «клиенты» сливаются в один, и per-IP тесты падают.
- **Берётся последний адрес из `X-Forwarded-For`, а не первый.** На этапе 3 nginx дописывает в конец свой адрес, и все клиенты станут одним.
- **Правила меняются в памяти, но не в БД** — после `docker compose restart app` вернутся значения из `.env`.
- **`Retry-After` не совпадает с `retry_after` в теле** или равен 0.
- **Правила перечитываются из `.env` при каждом старте и затирают изменённые через `PUT`.** Значения из `.env` — только начальные: записывайте их, если в БД правил ещё нет.
- **`openapi.yaml` не обновлён** после изменения маршрутов — CI перечислит, какие операции есть только в спецификации, а какие только в коде.
- **ruff ругается на порядок импортов в миграциях.** `make format` исправит сам.
- **Добавили зависимость — закоммитьте `uv.lock`.** Ставьте пакеты через `uv add <пакет>`: он обновит и `pyproject.toml`, и `uv.lock`. CI ставит зависимости строго по локу и с несинхронным локом падает.
- **Файл compose называется не `docker-compose.yml`.** CI ищет именно это имя в корне репозитория.
