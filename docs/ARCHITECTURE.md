## Сценарии

Бэкенд-приложение ограничивает частоту обращений к ресурсу `/resource` по двум правилам: общий глобальный лимит и лимит на клиента по IP. Возвращает решение пропустить/отклонить запрос. Референс: Envoy Rate Limit Service, NGINX `limit_req`.

1. Глобальный лимит на `/resource`. Все запросы к `/resource` суммируются в один счётчик. При превышении общего лимита сервис временно отклоняет дальнейшие запросы до обновления окна.
2. Индивидуальный лимит по IP. Для каждого IP действует отдельный счётчик. Если конкретный IP исчерпал свой лимит, его запросы к `/resource` отклоняются, даже если общий лимит ещё не выбран.
3. Оперативные изменения и устойчивость. Оператор меняет значения глобального и/или per-IP лимита — новые правила начинают действовать без перезапуска. После перезапуска сервиса правила сохраняются.
4. Несколько экземпляров (этап 3). Сервис работает в двух экземплярах за балансировщиком, лимиты при этом общие, а не удваиваются.

## Функциональные требования

- Поддержать один выбранный алгоритм лимитирования: fixed window, sliding window или token bucket (выбрать и кратко обосновать).
- Общий (глобальный) лимит на все запросы к `/resource`.
- Пер-IP лимит на запросы к `/resource`. IP клиента — первый адрес из заголовка `X-Forwarded-For`, если заголовка нет — адрес соединения.
- Отклонённый запрос — 429 с заголовком `Retry-After` (через сколько секунд имеет смысл повторить).
- Изменение правил без рестарта; персистентность правил между перезапусками. Начальные значения правил — из переменных окружения.
- Этап 3: два экземпляра сервиса за nginx; счётчики общие для экземпляров и хранятся в Redis.
- Этап 3: `/resource` продолжает применять действующие правила, когда PostgreSQL недоступен.

## Нефункциональные требования

- DAU (уникальных пользователей в день) — 10 000, MAU (в месяц) — 100 000.
- p95 времени ответа основного эндпоинта — меньше 100 мс.
- Доступность — 99,5 %.
- Данные не теряются при перезапуске сервиса.

Допущения для оценки: каждый активный пользователь обращается к `/resource` в среднем 100 раз в день; в пике нагрузка в 10 раз выше средней; один клиентский IP в среднем приходится на 2 пользователей; окно лимита — 60 секунд.

## Контракт API

Полная спецификация — в [`docs/openapi.yaml`](openapi.yaml), её пишете вы на этом этапе. Обязательные операции:

| Метод | Путь | Тело | Ответ | Коды |
|---|---|---|---|---|
| GET | `/resource` | — | `{"message": "ok"}` | 200; 429 — `{"detail": "rate limit exceeded", "retry_after": 7}` + заголовок `Retry-After: 7` |
| GET | `/limits` | — | `{"global": {"limit": 100, "window_seconds": 60}, "per_ip": {"limit": 10, "window_seconds": 60}}` | 200 |
| PUT | `/limits` | то же тело | то же | 200; 422 — `limit < 1`, `window_seconds < 1` |
| GET | `/health` | — | `{"status": "ok"}` | 200; 503 — PostgreSQL (с этапа 3 и Redis) недоступен |

На этапе 3 у каждого ответа появляется заголовок `X-Instance` — имя экземпляра (hostname контейнера), который обработал запрос.

Ошибки — JSON `{"detail": "..."}`, ошибки валидации — 422 в формате FastAPI.
